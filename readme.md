# 嵌入式机器人代码框架  

## 概述  
该代码是由本人设计的RoboMaster竞赛的嵌入式软件框架，基于STM32 HAL库与FreeRTOS实时操作系统构建。它采用BSP、Module、APP三层架构设计，旨在实现硬件驱动、功能模块与上层应用的解耦，提升代码的复用性、可维护性与不同机器人平台间移植效率。
## 项目框架  

| 层级 | 名称 | 主要内容                            |  
| ------- | ------- |---------------------------------|
| BSP | 硬件支持包 | USART、CAN、PWM等外设在HAL库基础上进一步封装   |
| Module | 外设模块层 | 继承自BSP类，实现如具体外设功能如上位机通信协议、电机控制等 |
| APP | 应用层 | 整合各模块，实现机器人底盘、云台等功能             |
  
## 框架目标
### 统一代码库
通过完善 BSP 与提供丰富的 Module，建立团队共享的代码框架。
### 降低移植成本
当更换机器人兵种或发生硬件改动时，通常只需修改或增补 App 层业务逻辑及少量外设模块，核心驱动与通用模块无需重写。
### 提升开发效率
电控同学可将精力集中于机器人策略与性能优化，而非重复编写底层驱动。

## 接下来要做什么
- **大云台电机没法用**：大云台原先是MF9025电机，后我将该电机换到轮腿上，并给大云台换上了MS9025电机，而MS9025电机转速只有20rpm，不换个电机根本没法用。且底盘已经是两年的老资历了，在换电机之前小陀螺时会出现整个大云台roll在微微动，目前很难定位是哪里机械结构有问题，机械组说可能整个底盘都得换。
- **拨弹盘PID**：现拨弹盘是3D打印的版本，经过岁月风霜已经卡弹了，故我无法测试拨弹盘设定的目标转速和转速PID是否合理。
- **云台优化**：原先云台使用单环控制，为补偿6020电机电压控制实际上未能等效为速度控制的问题，将KD调的极大，就会出现如果目标角度跳变时微分项会产生尖峰，发生剧烈抖动。现将单环改为串型双环，在原先角度环后加上速度环，比原本稳定多了，但是发现云台向下转到某个角度时再往上有概率出现摩擦突然增大的情况（原本单环时遇到的问题估计也是叠加在这个问题上产生的），所以现在速度环和角度环PID都只有KP（加上KI、KD后在克服突然的摩擦后摩擦力骤降过冲就开始震荡了），实际角度和目标角度会存在不确定的静差，在机械结构修复后再进一步优化参数。此外在上位机控制时的效果可能与遥控器的连续控制不同，尽早开始与视觉联调。（最好做好做半自主、云台手的准备，防止最后未实现自瞄而哨兵没有任何作用）（注：上面原因大多是本人根据看到的现象的推测）
- **任务独立**：该代码最初将Module的实例直接挂在chassis或gimbal的结构体下，而非现在的通过`Get_XXX_Ptr()`将实例指针挂在总结构体下，导致如果某个Module（如遥控器）如果两个任务（如云台和发射机构）都要，则只能将两个任务合并为一个任务，并通过分时复用来达成一个小的线程管理的效果。现将Module的注册与实例指针的挂载解耦，便可以将现放在不同ctrl_loop里的任务独立为不同的FreeRTOS任务，这样每个任务的代码可以放在不同文件里，不用像现在这样全在`chassis.c`和`gimbal.c`里面又臭又长，找一段代码找半天。
- **串口发送**：现在的串口发送为实现线程安全，将所有发送都放入邮箱，再由一个线程单独进行发送，但后续开发过程发现在当前写法下实际上很少会要多线程发送（所有发送任务都放在一个任务里），所以可以改为直接DMA发送，就不要一个额外的任务开支了。（具体写法参考我轮腿的代码https://github.com/da-zhexue/wheelleg_dm）
- **守护线程**：现在的`daemon.c`只有一个颜色不断变化的灯，用来指示任务调度还活着，后续可以在每个Module里加上上次获取到回调的时间（通过DWT），在`daemon.c`里判断当前距离上次得到回调的时间有无超时来判断设备是否离线。（不过每个Module都加太麻烦了，并且上场后离线了也救不了，所以一直没做，但在刚接收这个项目时加上这个可以更好地判断是哪出了问题）
- **统一设备**：将同一类的设备的命名统一，如所有电机编码器获得的数据都要包含相同的重要部分（力矩、速度、角度），并统一为相同的单位，手动将不同家电机的标准统一，这样在后续将电机更换时代码修改的量就非常少了。（说到这里有点想要C++的虚函数，实现一个电机的基类，之后所有电机都在继承该基类上重写发送、接收函数，这样更改硬件设备只要改个初始化，其他代码都不用动。不过一是嵌入式C++需要解决非常多的C++与C语言代码的互相调用的问题，二是虚函数会带来额外的性能消耗，括号里说的大抵是没法实现的）
- **注**：上面几个要做的是按重要顺序排列的，前三个问题与机械结构有关，必须解决，后面几个主要是代码优化，让代码看起来舒服。
如果你发现某些Module有问题可能在其他代码里可以发现修复好的，可以找找看，其他代码也有些该项目没有的Module（如天地飞遥控器、VESC电机等），如果要用到的话直接复制过来在CMakelists里加上就行了（https://github.com/da-zhexue/wheelleg_dm及https://github.com/da-zhexue/sentry26/tree/robovolley26）
